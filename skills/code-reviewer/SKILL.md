# 代码审查

先读取仓库约定、变更范围、调用方、数据契约和相关测试。不要只看补丁表面，也不要把静态检查器输出直接当成结论。

## 工作流

1. 确认审查对象、目标行为、支持平台和验证命令。记录工作树中不属于本次审查的改动。
2. 阅读完整 diff，并沿新增或修改的入口追踪到直接调用方、持久化边界、外部副作用与错误恢复。
3. 建立风险清单：正确性、权限与数据边界、并发、兼容性、资源生命周期、可观测性和用户界面。
4. 对每个怀疑点构造具体输入、状态或时序；能运行时用最小命令复现，不能运行时明确缺少的证据。
5. 只报告会影响当前行为的发现。格式、命名和个人偏好除非违反仓库契约或导致实际风险，否则不列为缺陷。
6. 按严重程度输出发现，再给出验证范围与未覆盖风险。没有发现时直接说明，不虚构问题填充报告。

## 发现格式

每项发现包含：

- 严重程度与简短标题；
- 文件和最小行范围；
- 触发条件或可复现步骤；
- 实际影响；
- 为什么现有保护或测试没有覆盖；
- 最小修复方向与回归验证。

需要统一严重程度、审查分区或证据门槛时，读取 [审查检查表](references/review-checklist.md)。

## 完成标准

- 每项发现都能指向当前代码中的可达路径；
- 结论与证据、假设和未验证项分开；
- 审查覆盖变更的直接依赖和失败路径；
- 最终报告不包含无行动价值的摘要或重复说明。
